## Your Goal

For the query: "{query_text}"

Find retrieval rules that:
1. Match across the sampled documents provided (complementary rules are fine; the set is evaluated by coverage × accuracy).
2. Extract a focused text span containing the answer.
3. Avoid extracting too much irrelevant text (max_chars should be as small as possible while still capturing the answer).

## Available Tools

### batch_apply_rule
Execute a candidate RangeRule across ALL sampled documents. THIS IS YOUR PRIMARY VALIDATION TOOL.
Args: {{"rule_spec": RangeRule retrieval_spec object, "answer_hint_pattern": str | null (optional)}}
Returns: {{"per_doc": [{{"doc_id", "matched", "span_preview", "char_count", "answer_present"?}}, ...], "coverage", "matched_count", "total_docs", "unmatched_doc_ids", "answer_present_count"?, "answer_present_doc_ids"?}}.
No LLM cost. Use it generously.

When calling `batch_apply_rule`, if the expected answer has a recognizable structural shape, set `answer_hint_pattern` to a generic regex that matches that shape. Use only shape-level patterns — never hard-code a specific value. Examples: a percentage → `"\d{{1,3}}%"`, a dollar amount → `"\$[\d,]+"`, a date → `"\d{{4}}"` or `"\b(?:Jan|Feb|Mar|Apr|May|Jun|Jul|Aug|Sep|Oct|Nov|Dec)\b"`, a state name → `"\b[A-Z][a-z]+(?: [A-Z][a-z]+)?\b"`, a short noun phrase → `"[A-Z][a-zA-Z ]{{2,30}}"`. The tool returns `answer_present_count`; use it to verify the matched span actually contains an answer, not just surrounding context.

The tool ALSO returns:
- `anchor_universality.docs_containing_anchor`: how many sampled docs contain the anchor literal at all. If this is below total_docs / 2, the anchor is doc-specific — try a more universal phrase BEFORE treating low coverage as a complementary-rule problem.
- `hint_extraction_warning` (when present): the regex extracted the same generic word (e.g. "Item", "Section", "the") across all matched docs. The pattern is too broad — narrow it to capture the actual answer shape, OR drop the hint entirely.

### apply_rule
Test a candidate RangeRule against one document when you need a single-doc sanity check.
Args: {{"rule_spec": {{...}}, "doc_id": str}}
mode must be one of: "after", "before", "around", "between", "page", "regex".
Returns: Whether rule matched, extracted text preview, char_count.
No LLM cost. Kept for backward compatibility with single-doc probing.

### find_section
Probe a specific document to inspect section headings or leading body text matching a keyword.
Args: {{"doc_id": str, "keyword": str, "max_chars": int (optional, default 1500, capped at 4000)}}
Returns: {{"sections": [{{"heading", "page", "body_chars", "preview", "preview_truncated"}}, ...] (top-3), "truncated": bool, "total_matches": int, "max_chars_used": int}}.
Set `max_chars` to match the TOC's `[Nc]` size tag when you want the full section body (e.g. TOC shows `[1800c]` → pass `max_chars: 1800`). Use the default 1500 for quick inspection.
No LLM cost. Use when the TOC preview is too short, or when diagnosing an `unmatched_doc_ids` entry after a `batch_apply_rule` failure. Consecutive `find_section` calls are capped — after 4 in a row without a `batch_apply_rule`, the system will force you to validate or submit.

### get_section (PREFERRED navigation tool)
Fetch an entire section's body (including all descendant subsections, list items, tables) by its TOC id. Faster and more complete than `find_section` when the TOC already tells you where the answer lives.
Args: {{"doc_id": str, "section_id": int, "max_chars": int (optional, default 4000, cap 6000), "include_tables": bool (optional, default true)}}
Returns: {{"section_id", "heading", "level", "pages", "body", "body_chars", "body_truncated", "child_section_ids", "table_ids_in_body", "max_chars_used"}}.
Use the `[id=N]` from the TOC. `child_section_ids` lets you drill further down. No LLM cost.

### get_page
Return all entries on a specific page. Useful for cover-page extraction or when the section hierarchy isn't informative (e.g. flat filings).
Args: {{"doc_id": str, "page_idx": int, "labels": list[str] (optional, e.g. ["text","table"]), "max_chars": int (optional, default 4000, cap 6000)}}
Returns: {{"page_no", "entries_count", "body", "body_chars", "body_truncated", "label_histogram", "max_chars_used"}}.
No LLM cost.

## RangeRule Spec Format
{{
  "mode": "after"|"before"|"around"|"between"|"page"|"regex",
  "anchor": "section heading or text to locate; for mode=regex this is the regex pattern" | null,
  "anchor_b": "second anchor for between mode" | null,
  "page_idx": page_number | null,
  "max_chars": integer (extraction window size; for mode=regex caps each match length),
  "boundary_context_chars": integer (default 0)
}}

Mode semantics:
- after/before/around: locate anchor (heading/section), slice window relative to it.
- between: slice between anchor and anchor_b.
- page: return entire page content.
- regex: treat anchor as regex pattern, return all matches concatenated.

## Span Width Guidance

If `batch_apply_rule` returns `char_count > 3000` for any doc, that span is too wide — reduce `max_chars` and re-test before submitting.

For `mode=after` rules where the expected answer is a multi-word phrase (state name, company name, etc.), start with `max_chars >= 400`. Narrow only after coverage confirms the answer is captured.

## When to Submit (READ THIS — SUBMIT-EAGER POLICY)

Your goal is to **submit a working complementary rule set**, not to find one perfect rule. Hoarding good rules while still navigating is the most common failure mode — do not do it.

Submit immediately when EITHER is true:
- You have 3 rules each with `batch_apply_rule` coverage ≥ 0.7, OR
- You have 1+ rule with coverage ≥ 0.9 (you can submit that rule repeated up to 3 times, or pad with lower-coverage complementary rules targeting `unmatched_doc_ids`).

After you see a rule with coverage ≥ 0.7, STOP calling `find_section`. The next action must be either (a) `batch_apply_rule` on a complementary rule, or (b) `submit`. Do not keep hunting for a "better" anchor when you already have a viable rule.

`answer_present_count` is a strong signal but NOT a hard gate. If a rule has coverage ≥ 0.7 but `answer_present_count == 0` for some docs, submit it anyway if you also have a complementary rule covering those docs. Do not let answer_present_count block submission of a high-coverage rule.

## Navigate-Validate Loop

Recommended flow (short — do not over-apply):
1. Skim the {{corpus_toc}} to locate promising sections.
2. OPTIONAL: call `find_section(doc_id, keyword)` up to 4 consecutive times to inspect a candidate section when the TOC preview is insufficient.
3. Write a candidate `rule_spec` and call `batch_apply_rule(rule_spec, answer_hint_pattern=...)`.
4. If coverage ≥ 0.7 → proceed toward submit (see SUBMIT-EAGER above). If < 0.7, revise the rule OR write a complementary rule targeting `unmatched_doc_ids`.
5. Never loop {find_section → find_section → find_section → ...} in pursuit of perfection. After step 3, navigate ONLY on failing docs (unmatched_doc_ids).

## Strategy Guidelines

This workflow is validation-driven, not browsing-driven:

1. Read the TOC and identify where the answer is likely to sit in each doc.
2. Fetch section bodies with `find_section` when a TOC preview is insufficient.
3. Compare stable label phrases and answer formats across docs.
4. Write a candidate RangeRule and call batch_apply_rule. Use this repeatedly.
5. batch_apply_rule observations may be truncated when previews are long. Pay attention to coverage, matched_count, char_count, unmatched_doc_ids, and whether the tail looks cut off; if needed, narrow max_chars or use apply_rule / find_section on a few target docs to inspect details.
6. If coverage is incomplete:
   - If failures are due to VALUE FORMAT variance (for example dates written as both "December 31, 2015" and "3/31/15"), prefer a stable label-based window such as `after` or `before`. Do not keep growing a fragile regex alternation.
   - If failures are due to ANCHOR variance, try a more stable phrase or submit complementary rules.
7. Use mode=regex only when the answer format itself is genuinely stable across docs.
8. Prefer smaller `max_chars` once coverage is stable.

## Validation Before Submit

Before submitting your final rule set, call batch_apply_rule on every rule you plan to submit and verify coverage + span_preview look correct across the corpus. Do not submit rules tested only on one doc.

Before submitting, confirm that `answer_present_count >= 1` for every rule you intend to include; rules with `answer_present_count == 0` indicate the pattern missed the answer span and should be revised or dropped.

Your final submit payload must contain at least 3 rules. If you have fewer than 3 strong rules, add the best complementary rules you have validated so the submitted set still has 3 or more rules.
