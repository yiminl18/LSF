## Reflection goals
1. Keep the final representation atomic: one rule = one retrieval_spec.
2. Fix rules that miss anchors, use the wrong direction, or choose the wrong section/page boundary.
3. Reduce retrieval cost when regions are too large.
4. Preserve rules that already work well.

## Failure-to-fix heuristics
- `anchor_not_found` / `anchor_pair_not_found`: prefer a more literal, more stable, cross-document-consistent anchor or section boundary.
- `page_not_found`: remove or relax brittle page restrictions unless the page is clearly stable.
- `retrieval_too_large`: reduce `max_chars` or replace a broad rule with a tighter anchor/boundary.
- `gen_not_found`: the rule matches, but the answer span is still missing or obscured; change direction, move the boundary, or add a small `boundary_context_chars` when the answer looks adjacent to the boundary.
- `judge_false`: the retrieved region likely contains too much noise or the wrong slice; tighten the boundary, use a better anchor pair, or keep the broad rule only as a fallback while adding a stricter companion rule.

## Rule family coverage
- Prefer a bundle whose rules cover meaningfully different retrieval families when the current family is failing.
- Useful families include:
  - `page` / physical-location rules
  - single-anchor direction rules (`after` / `before`)
  - two-anchor boundary rules (`between`)
  - heading or section-neighborhood rules
  - keyword-neighborhood or label-neighborhood rules
  - relative-position patterns such as "value appears immediately before/after a label"
- If several failing rules are merely near-paraphrases of the same family, replace at least one with a different family instead of making more tiny wording edits.

## Direction and boundary reasoning
- Explicitly ask: is the answer more likely BEFORE the anchor, AFTER the anchor, or straddling the anchor boundary?
- If a field label or caption appears after the value in the sample docs, prefer `before` or a small `boundary_context_chars` rather than repeating `after` variants.
- If a rule keeps matching a broad section but generation returns `Information not found.`, try a more local subsection, boundary pair, keyword neighborhood, or page restriction instead of only shrinking `max_chars` on the same broad span.
- For list-style or category-style questions, prefer rules that target local enumeration or concentrated noun-phrase neighborhoods rather than only long introductory prose.
- Prefer anchors that are stable landmarks: headings, labels, captions, recurring field names, page markers, or repeated section boundaries.
- If a failing rule uses an answer-like content phrase or one-off entity list as the anchor, replace it with a more structural landmark rather than paraphrasing the same phrase.

## Bundle design goals
- Do NOT make all rules nearly identical.
- If one stable rule already covers the sample documents cleanly, prefer keeping that single rule instead of forcing a ladder.
- If you emit multiple rules, try to maintain a useful range ladder:
  - a tight high-precision rule,
  - optionally a medium rule,
  - at most one broader fallback rule.
- If tight rules often fail with anchor misses, keep or add a broader fallback.
- If broad rules often fail with `gen_not_found` or `judge_false`, add or keep a tighter boundary-aware rule.
- A fallback rule must differ by family or boundary logic, not just by being a slightly larger copy of the same rule.
- If the current bundle has collapsed into one family and keeps failing, diversify before making it even tighter.
- If a candidate rule is anchored on content that appears to be part of the answer itself, treat it as suspicious unless the sample docs show it is a stable landmark across documents.

## Optional boundary context
- `boundary_context_chars` is a non-negative integer.
- Use it only when a small amount of context just outside the main boundary is helpful.
- Semantics:
  - `after`: include up to `boundary_context_chars` characters BEFORE the anchor in addition to the main forward window.
  - `before`: include up to `boundary_context_chars` characters AFTER the anchor in addition to the main backward window.
  - `between`: expand BOTH sides of the main span by up to `boundary_context_chars`.
  - `around` and `page`: set `boundary_context_chars` to `0`.
